4. 질문 유형 분류기 (Classifier)

타입 1~4 분류 정확도는 전체 응답 품질을 결정하는 가장 중요한 단계다. 분류 오류는 완전히 다른 경로를 실행시키므로, 아래 프롬프트와 퓨샷 예시를 그대로 사용한다.

4.1 분류기 API 호출 설정

항목 값 이유
model claude-sonnet-4-20250514 Haiku보다 분류 정확도 높음
max_tokens 100 JSON 결과만 받으므로 낮게 설정 (비용 절감)
temperature 0 분류 일관성 확보

4.2 시스템 프롬프트

You are a query classifier for SUBLENS, a subscription management platform.
Classify the user's question into exactly one of four types.

TYPE DEFINITIONS
- type_1: Queries about the user's own subscription data (amounts, dates, counts, history).
  Requires SQL lookup against the user's subscription records.
- type_2: Queries about how to use SUBLENS itself (features, limits, billing, UI).
  Answered from SUBLENS FAQ documents only.
- type_3: Queries about specific bundle product terms, conditions, or specs
  (contracts, cancellation, family sharing, eligibility).
  Answered from bundle catalog documents only.
- type_4: Queries asking for optimization, comparison, or recommendations
  involving the user's own subscriptions AND bundle products together.

AMBIGUITY RULES
- If the question could be type_1 OR type_4, choose type_4.
- If the question mentions a bundle name but only asks about its terms, choose type_3.
- If completely unrelated to subscriptions, classify as type_2 and answer with FAQ fallback.

OUTPUT FORMAT — return only valid JSON, no explanation, no markdown:
{"type": "type_1"|"type_2"|"type_3"|"type_4", "confidence": 0.0-1.0, "reason": "one sentence"}

4.4 엣지 케이스 처리 규칙

패턴 분류 근거
"나한테", "내 구독이랑" + 번들 언급 type_4 1인칭 + 번들 조합은 비교 추천 의도
번들 이름 단독 + 약관/조건 질문 type_3 추천 의도 없으면 번들 DB 조회로 충분
confidence < 0.55 type_2 폴백 낮은 확신 시 FAQ 안내로 안전하게 처리
JSON 파싱 실패 type_2 폴백 분류기 오류 시 안전한 경로로 라우팅

4.5 분류기 코드 (classifier.py)

_client = anthropic.Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))
FALLBACK_CONFIDENCE = 0.55

def classify_query(question: str) -> dict:
    user_content = f"{FEWSHOT_EXAMPLES}\nUser: {question}"

    message = _client.messages.create(
        model="claude-sonnet-4-20250514",
        max_tokens=100,
        temperature=0,
        system=CLASSIFIER_SYSTEM_PROMPT,
        messages=[{"role": "user", "content": user_content}],
    )
    raw = message.content[0].text.strip()

    try:
        result = json.loads(raw)
        if result.get("confidence", 0) < FALLBACK_CONFIDENCE:
            result["type"] = "type_2"
        return result
    except (json.JSONDecodeError, KeyError):
        return {"type": "type_2", "confidence": 0.0, "reason": "분류 실패 — FAQ 폴백"}

5. SQL 경로 상세 — 타입 1 (NL2SQL + 보안)

5.1 처리 흐름

사용자 질문

    ↓

[Step 1] Claude Sonnet — SQL_SCHEMA_PROMPT 기반 SQL 생성 (max_tokens: 300)

    ↓

[Step 2] 마크다운 코드 펜스 제거 + MySQL→PostgreSQL 구문 교정

    ↓

[Step 3] 위험 키워드 차단 (INSERT, UPDATE, DELETE, DROP 등)

    ↓

[Step 4] WHERE user_id = '{user_id}' 강제 주입

    ↓

[Step 5] PostgreSQL 실행 → 결과 행 반환

    ↓

[Step 6] Claude Sonnet — SQL 결과 + 대화 이력 → 자연어 답변 생성

5.2 보안 레이어

단계 방법 구현
1. 스키마 제한 LLM에게 subscriptions, users, bundle_catalog 3개 테이블만 노출. password_hash 등 민감 컬럼은 프롬프트에서 제외 SQL_SCHEMA_PROMPT
2. userId 강제 주입 LLM이 생성한 SQL에 WHERE user_id = '{userId}'를 실행 직전에 무조건 주입. 기존 WHERE가 있으면 AND로, 없으면 WHERE로 추가. ORDER BY/GROUP BY/LIMIT 앞에 정확히 삽입. _inject_user_id()
3. 위험 키워드 차단 INSERT, UPDATE, DELETE, DROP, TRUNCATE, ALTER, CREATE, REPLACE, MERGE, EXEC, EXECUTE 정규식 검사 _is_safe_sql()
4. PG 구문 교정 MONTH(col)→EXTRACT, YEAR(col)→EXTRACT, CURRENT_DATE()→CURRENT_DATE 자동 변환 _fix_pg_syntax()

5.3 SQL 스키마 프롬프트 (Claude에게 노출되는 테이블 정보)

Available tables:
- subscriptions: id, user_id, service_name, amount, billing_cycle, status,
                 next_billing_date, billing_day_of_month, is_bundle, bundle_id
- users: id, name, mobile_carrier
- bundle_catalog: id, provider, plan_name, base_price, includes, telecom_exclusive, is_active

Rules:
- Generate SELECT SQL only
- Do NOT include user_id in WHERE clause (it will be added automatically)
- Return only the SQL query, nothing else

PostgreSQL syntax: EXTRACT, CURRENT_DATE, ILIKE...
Value casing: status='ACTIVE'|'INACTIVE'|'CANCELLED', billing_cycle='MONTHLY'|'YEARLY'|'WEEKLY'

Bundle subscription rules:
- is_bundle = true → 번들 상품 (포함 서비스 합산 아님, amount 그대로 사용)
- bundle_id → bundle_catalog.id JOIN 가능

5.4 Claude 호출 설정

단계 모델 max_tokens 용도
SQL 생성 Sonnet 4 300 SQL만 반환
답변 생성 Sonnet 4 500 SQL 결과 → 자연어 변환

6.3 시스템 프롬프트 핵심 규칙

  • "문서", "참고 문서", "가이드" 등의 출처 단어를 답변에 노출하지 않음
  • 참고 정보에 없는 내용은 "안내드리기 어렵습니다" 안내
  • 구독과 무관한 질문(날씨, 스포츠 등)은 구독 관련 질문 유도
  • 마크다운 사용 금지 (번호 목록과 하이픈 목록만 허용)

6.4 폴백 처리

ChromaDB 컬렉션이 존재하지 않거나 비어 있으면 "사용 가이드 데이터가 아직 준비되지 않았습니다." 메시지를 반환한다.

8. 구독 최적화 엔진 — 타입 4 CHANGED

핵심 설계 원칙: 모든 비용 계산은 Python이 수행하고, Claude는 서술(summary)과 주의사항(cautions)만 작성한다. Claude가 생성한 숫자가 Python 계산 결과와 다르면 Python 값으로 강제 복원한다 (수치 환각 방지).

8.1 전체 처리 흐름

[Step 1] DB 병렬 조회 (asyncio.gather)

    ├─ 사용자 구독 목록 (subscriptions WHERE status='ACTIVE')

    └─ 사용자 통신사 (users.mobile_carrier)

    ↓

[Step 2] 번들 후보 조회 (통신사 필터 + 이미 가입한 번들 제외)

    ↓

[Step 2.5] 가상 시나리오 감지 ("~에 가입하면" 키워드) → 해당 시 Early Return

    ↓

[Step 3] Claude Haiku — 서비스명 정규화 (구독명 ↔ 번들 includes 매칭용)

    ↓

8.3 Python 계산 엔진 (type4_calculator.py)

서비스명 매칭 전략

  • 한/영 동의어 사전: 넷플릭스↔netflix, 유튜브 프리미엄↔youtube premium 등 30+ 매핑
  • 복합 구독명 분리: "넷플릭스 + 유튜브 프리미엄" → 개별 토큰으로 분리 후 각각 매칭
  • 부분 포함 허용: 짧은 쪽이 긴 쪽의 60% 이상이고 3글자 이상일 때
  • Haiku 정규화: 위 규칙으로 매칭되지 않는 이름을 Claude Haiku가 번들 includes 기준으로 보정

최적화 알고리즘

def calculate_optimization(subscriptions, bundles) -> dict:
    # 1. 월 환산 금액 계산 (YEARLY → /12, WEEKLY → *52/12)
    # 2. 개별 구독만 교체 대상 (is_bundle=true인 기존 번들은 고정 비용)
    # 3. 각 번들 후보에 대해 교체 가능 구독 매칭 → 절약액 산출
    # 4. 양의 절약액을 가진 후보만 선별
    # 5. 2^n 비트마스크 완전탐색 (최대 20개 후보, 구독 중복 사용 불가)
    # 6. 전역 최적 비겹침 번들 조합 선택
    # → current_total, optimized_total, savings, recommended_bundles, keep_subscriptions
성능 보장: 후보 수가 20개를 초과하면 절약액 상위 20개만 완전탐색. 실제 번들 카탈로그 규모(~50개) 중 통신사/절약 필터 후 남는 후보는 대체로 10개 미만이므로 2^10 = 1,024회 이내에 종료된다.

9. Conversation Memory CHANGED

v1.2와의 차이: LangChain ConversationSummaryBufferMemory 대신 Redis에 JSON 배열로 직접 저장하는 경량 방식을 채택. 요약 LLM 호출이 없어 비용과 지연이 없으며, MAX_MESSAGES 상한으로 크기를 통제한다.

9.1 구현 방식

항목 설정
저장소 Redis (redis://localhost:6379)
직렬화 JSON 배열 ([{"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}, ...])
메시지 상한 20개 (10턴 = 10질문 + 10답변)
TTL 7,200초 (2시간)
초과 처리 오래된 메시지 순차 제거 (요약 없이 단순 슬라이싱)

9.2 Redis 키 설계

키 패턴 값 TTL 용도
conv:{session_id} JSON 배열 (대화 이력) 7,200초 모든 타입의 대화 히스토리
calc:{session_id} JSON 객체 (최적화 계산 결과) 7,200초 타입 4 팔로업 질문 시 재활용

9.3 히스토리 활용 방식

각 에이전트는 Claude API 호출 시 히스토리를 messages 앞에 prepend하여 맥락을 유지한다:

history = mem.get_history(session_id)
messages = history + [
    {"role": "user", "content": f"[참고 정보]\n{context}\n\n[사용자 질문]\n{question}"}
]
# → Claude API messages 파라미터로 전달

9.4 저장 시점

에이전트 실행 후 routes/query.py에서 mem.append_turn()을 호출하여 저장. type_4 dict 응답은 json.dumps()로 문자열 변환 후 저장한다.
